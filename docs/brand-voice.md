# 品牌语言

## 名称与主张

**Kepos Communis**，简称 Kepos。Kepos 意为花园。

品牌主张：**让效率回到人的目的。**

## 产品介绍

Kepos Communis 是人调度 Agent 进行分工工作的终端空间。一位总理 Agent 组织工作，48 个代表席承接不同领域的任务，Worker 执行具体委派。人提出目标、检查报告，并决定下一步。任务结果和运行记录可在工作台中查阅。

简短介绍：**一位总理 Agent，48 个代表席，由人决定工作的方向。**

48 席是产品的重要特点，应在首页介绍中直接说明。首次预置十个常用代表，任务按需派发；不要写成默认常驻运行 48 个自治角色。单池最多并行处理 48 项任务，多池尚未统一调度。

## 写作依据

Kepos 的产品立场受到法兰克福学派对工具理性和人的自主性的讨论启发。文案关注分工中实际发生的事：人是否知道任务为何被执行，能否检查依据，能否改变安排。

这些问题可以用普通语言说明，不必在功能介绍里反复使用“异化”“解放”等理论术语。不冒充学者引文，也不把多 Agent 协作直接等同于社会中的民主制度。

## 称谓

| 产品称谓 | 工程对应 |
| --- | --- |
| 人、你 | 使用者或操作者，可以委派，也可以亲自介入 |
| 总理 Agent | 主 Agent、主 Pi 会话，负责组织与汇总 |
| 代表 Agent、代表席 | Council 中配置的领域职责、模型和 Skill |
| Worker | 承载具体任务的执行单元 |
| 长程计划 | Mission，以依赖关系组织步骤 |
| 运行证据 | 任务产出、配置快照、事件、回执和哈希 |

CLI、工具与类型名称按实际接口书写，例如 `orbital_delegate`、`WorkerPool`。

## 怎么写

- 开头先说产品是什么、提供什么，安装说明直接给步骤。
- 写功能时说明具体操作和结果。例如“按 F10 查看 48 个代表席”，比“让协作变得可见”更有用。
- 一段只说明一件事。不把每个段落都写成口号，不连续使用对仗、三项排比或“不是……而是……”。
- 保留必要的技术条件。48 项并发是单池上限；保存计划不保证重启续跑；收到取消请求不表示远端进程已经退出。
- 失败提示先说错误，再说能做什么。没有发生的动作不要写成成功。
- 品牌主张在首页出现即可，不需要每章再解释一次。哲学背景放在产品说明，工程文档以事实为主。

## 操作提示

| 场景 | 示例 |
| --- | --- |
| Council | 按 F10 查看代表席；Tab 切换任务列表。 |
| Mission | 查看步骤、依赖和等待批准的任务。 |
| 需要批准 | 此步骤需要批准。请先查看任务说明与依据。 |
| 任务完成 | 任务已完成，可查看结果和运行记录。 |
| 任务失败 | 任务未完成：〈错误原因〉。已有产出见任务详情。 |
| 已请求取消 | 已请求停止，正在等待退出确认。 |
| 代理审批 | 当前允许模型批准门禁。 |

提示中的动作必须与实际状态一致。“已有产出”只在确有产出时显示。

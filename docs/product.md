# Kepos Communis

Kepos 是人调度 Agent 进行分工工作的终端空间。工作台设有 **48 个代表席**，由总理 Agent 组织工作，代表 Agent 按领域分工，Worker 完成具体任务。你可以查看各项任务的进展、报告和运行记录，随时补充要求或调整安排。

## 48 个代表席如何工作

代表可以分别负责规划、调研、工程、风险、核验等工作。每位代表都有自己的职责、模型和 Skill 配置；处理具体任务时，也可以临时创建代表。

首次使用预置十个常用代表，不会一启动就运行 48 个任务。席位按需使用，单个执行池最多同时处理 48 项委派，多出的任务排队。按 `F10` 可以看到议会席位图，也可以切到任务列表，查看错误、待处理事项和完整结果。

| 角色 | 职责 |
| --- | --- |
| **人** | 提出目标和限制，检查结果，作出关键决定 |
| **总理 Agent** | 拆解目标、安排代表、汇总发现、核对依据 |
| **代表 Agent** | 负责一个领域，提交该领域的报告和建议 |
| **Worker** | 执行细项任务，返回产出、错误与运行记录 |

代表是职责配置，Worker 是执行单元。同一份代表配置可以用于多项任务。当前委派由总理发起，复制委派最多一层；具体对应关系见[工程架构](architecture.md)。

## 以项目调研为例

你可以这样提出任务：

> 调研这个项目。请分别检查工程结构、使用场景和主要风险，不要修改文件；报告中说明依据和需要进一步确认的问题。

总理把工作分给不同代表。Worker 读取资料、检查相关内容，代表分别交回发现，总理再整理成一份报告。如果两份调查的结论不同，报告应保留这种分歧，并说明各自依据，供你判断是否需要补充调查。

你不用等全部完成才介入。任务运行期间，可以查看进度、补充约束，或请求停止某项工作。遇到长程计划的门禁时，能否由模型代为批准取决于当前审批模式。

## 为什么保留人的判断

分工可以省去许多重复劳动，也容易让人离工作的过程越来越远：报告已经生成，却不清楚依据是什么；任务还在推进，却没有再问最初的目标是否合适。

Kepos 希望减少这种距离。它把任务、产出和运行记录放在一起，让人能够回看一项结论是怎样得到的。总理和代表可以提出建议，工作为何值得继续，仍由人决定。这是“让效率回到人的目的”在产品中的含义。

## 工作台

左侧是代表席，中间是与总理交谈和阅读报告的议案区，右侧列出项目与历史对话。需要看整体分工时打开议会，需要处理某项问题时进入任务详情。长程计划另有步骤列表，显示依赖关系和等待批准的事项。

| 入口 | 用途 |
| --- | --- |
| `F2` | 调整代表配置和审批模式，管理任务 |
| `F3` / `F8` | 查看当前会话或跨项目任务 |
| `F9` | 查看长程计划 |
| `F10` | 查看 48 个代表席或任务列表 |
| `Ctrl+X` | 请求中止；具体范围取决于当前视图 |

## 结果与运行证据

任务先返回短预览，完整内容按需读取。配置快照记录接受任务时的角色、模型和工具，回执与事件记录运行结果。哈希用于核对内容是否一致，不能证明报告中的判断正确。

证据有保留期限。超龄终态任务会按[保留策略](retention.md)清理；重要报告和产出应在清理前单独备份。

## 使用时需要知道

- 默认严格审批会对涉及门禁或 Kepos 数据的操作请求确认；代理审批允许模型批准门禁。只读监督和 MCP 各有权限范围，见[安全说明](../SECURITY.md)。
- Worker 默认使用只读工具，临时获授的 MCP 工具可能有写入能力。
- 保存计划后可以重新查看，但进程重启不保证任务自动续跑。无法确认的派发需要人工核对。
- 取消请求和进程已经退出是两个状态，远程任务尤其需要确认。

Kepos 适合项目调研、资料梳理、方案比较、工程评估和文档核验。需要承担专业责任的判断，仍应由相应的人审阅。
